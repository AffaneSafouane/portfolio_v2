# Ticket 6 — Internationalisation FR/EN : spécification

## Point de départ et arbitrage

À ce stade, les Tickets 1–5 ont créé huit familles de pages françaises : accueil, projets, fiches `/projects/[slug]`, expériences, veille/RSS, contact, mentions légales et confidentialité. `/api/contact` et `/feed.xml` existent aussi. Le Ticket 6 traduit **ce contenu final**, sans revenir à l'ancienne veille microservices ni aux anciennes cartes projet. Conserver toutes les URL françaises et ajouter `/en` et ses équivalents. Deux groupes de routes avec layouts racine sont retenus pour que `html lang` soit correct sur le premier HTML ; la navigation entre racines entraîne un chargement complet accepté. Écarter le paramètre `?lang=` et le middleware de réécriture pour rendre les URL explicites.

## Arborescence et routes

Supprimer `src/app/layout.tsx` après création de `src/app/(fr)/layout.tsx` (`<html lang="fr">`) et `src/app/(en)/layout.tsx` (`<html lang="en">`). Déplacer les sept `page.tsx` françaises dans `(fr)` : `/`, `/projects`, `/experiences`, `/tech-monitoring`, `/contact`, `/mentions-legales`, `/confidentialite`, ainsi que `src/app/(fr)/projects/[slug]/page.tsx`. Les nouveaux adaptateurs anglais sont sous `src/app/(en)/en/` : `/en`, `/en/projects`, `/en/projects/[slug]`, `/en/experiences`, `/en/tech-monitoring`, `/en/contact`, `/en/legal`, `/en/privacy`. Garder `src/app/api/contact/route.ts` et `src/app/feed.xml/route.ts` hors groupes ; ajouter `src/app/(en)/en/feed.xml/route.ts` pour les abonnés anglophones. `globals.css` est importé par les deux layouts, qui rendent un `SiteShell` serveur commun avec Header/Footer localisés. Les pages de détail restent statiques via les mêmes slugs publics.

## Contrats de langue et données

`src/lib/i18n/types.ts` exporte `Locale = 'fr'|'en'`, `PageId = 'home'|'projects'|'experiences'|'tech-monitoring'|'contact'|'legal'|'privacy'` et `Dictionary`. `src/lib/i18n/routing.ts` exporte `pathFor(locale,page)`, `projectPath(locale,slug)` et `getLocalizedPath(pathname,targetLocale)` ; les chemins légaux sont explicitement `/mentions-legales` ↔ `/en/legal` et `/confidentialite` ↔ `/en/privacy`. `getLocalizedPath` reconnaît d'abord les fiches via une table de slugs **publics** du Ticket 3, puis les sept pages statiques ; une route inconnue va à l'accueil de la langue cible. Les slugs restent en ASCII identiques dans les deux langues ; les noms de projet sont traduits, pas les slugs. Un projet draft n'obtient pas de route EN.

`src/lib/i18n/fr.ts` et `en.ts` exportent des dictionnaires satisfaisant `Dictionary`, `src/lib/i18n/index.ts` expose `getDictionary(locale)`. Clés : `nav`, `footer`, `home`, `projects`, `projectDetail`, `experiences`, `monitoring`, `contact`, `legal`, `privacy`, `feed`, `metadata`. `projectCopyFr` du Ticket 3 est conservé comme source des textes projets français ; créer `src/lib/projects/copy.en.ts: Record<ProjectId, ProjectCopy>`, référencé par le dictionnaire anglais. Le contenu éditorial veille du Ticket 2 est déplacé en copy de dictionnaire avec des IDs stables, sans dupliquer les faits ni les sources de flux. Les six expériences et les quatre aperçus issus du Ticket 4 gardent leurs IDs, dates, ordre et liens dans `src/lib/experiences/`. La copy française validée est déplacée sans changement de sens vers les dictionnaires ; les textes anglais utilisent les mêmes `ExperienceId`. Ne pas recréer `src/app/data/experience.ts` ni une seconde liste d'expériences. Les réponses de `/api/contact` restent des codes, traduits côté formulaire. `buildFeedXml(items)` du Ticket 2 devient `buildFeedXml(items, locale: Locale)` ; la route FR passe `'fr'` et la nouvelle route EN passe `'en'`. L'agrégation garde les titres originaux des éditeurs externes ; seules la page, les états, le canal `/en/feed.xml` et l'entrée éditoriale sont traduits.

## Frontière serveur/client

`src/components/pages/{HomePage,ProjectsPage,ExperiencesPage}.tsx` sont créés comme Server Components partagés ; `src/components/projects/{ProjectCard,ProjectDetailPage}.tsx`, `src/components/monitoring/MonitoringPage.tsx` et `src/components/legal/{LegalNoticePage,PrivacyPage}.tsx` sont adaptés en place, sans duplication. Les `page.tsx` des deux langues sont des adaptateurs minces transmettant `locale` ; les textes visibles viennent des dictionnaires ou `ProjectCopy`. `Header` et `LanguageSwitcher` client ne reçoivent que les libellés nécessaires, pas tout le dictionnaire. Le contact garde le widget Turnstile et reçoit la portion de copy `contact`. Les liens internes utilisent `pathFor`/`projectPath`; le sélecteur est accessible au clavier et garde la page, notamment la fiche projet et les pages légales. Les deux layouts ont des metadata de base localisées ; le travail canonical/hreflang exhaustif reste au Ticket 8.

## Acceptation et risques

Vérifier en accès direct les quatorze routes statiques, toutes les fiches publiques dans les deux langues, `/feed.xml` et `/en/feed.xml`. Les deux `<html lang>` sont corrects, le sélecteur conserve le slug, aucun texte UI résiduel n'est en dur dans les composants partagés et les états contact sont traduits. Tester mobile/desktop, clavier, RSS anglais, formulaire dans les deux langues, `npm run test`, `npm run lint`, `npm run build` et TypeScript. La vérification du HTML et du build doit prouver que les fiches sont pré-rendues ; le passage entre layouts provoque un rechargement de document, accepté. Les faits juridiques et techniques déjà validés restent identiques dans les deux traductions.
